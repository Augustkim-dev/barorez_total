## 3. 검증 과정에서 발견된 버그 (중요)

본 단위 검증에서 **컬럼명 미스매치 3건**이 발견되어 수정됨. 본 프로젝트는 매장 FK 컬럼명이 일관되지 않음:

| 테이블 | 매장 FK 컬럼 |
|---|---|
| 기존 (`orders_t`, `shop_menu_t`, `shop_category_t`, `cart_t` 등) | **`sh_idx`** |
| 신규 D1 (`print_client_t`, `print_route_rule_t`, `print_job_t`) | **`shop_idx`** |

D3 작성 시 신규 테이블 컨벤션을 따라 `$order['shop_idx']`로 읽었으나, `orders_t`의 실제 컬럼은 `sh_idx`. NULL → `(int)NULL = 0` → 매장 활성화 게이트 실패 → 빈 배열 반환.

수정된 컬럼명 3건:
- `$order['shop_idx']` → `$order['sh_idx']` (활성화 게이트 매장 추출)
- `$order['wdate']` → `$order['ot_wdate']` (페이로드의 order_time)
- `$order['ot_memo']` → `$order['ot_notes']` (페이로드의 memo)

**향후 시사점**: Phase 2의 Server C가 신규 `print_job_t.shop_idx`를 다룰 때는 일관성 유지(`shop_idx`), 단 PHP 측에서 orders_t나 다른 기존 테이블을 추가로 조회해야 하면 `sh_idx` 사용 — **이 비대칭을 다시 만나면 잊지 말 것**.

## 4. 검증 결과

### 검증 A — 회귀 (비활성 매장)

`print_enabled=0` 상태에서 기존 운영 주문 흐름이 정상 작동. print_job_t에 row 0건 추가. error_log에 hook 관련 메시지 없음.

### 검증 B — 활성 매장 (sh_idx=48 "소담한하루")

```sql
UPDATE shop_t SET print_enabled=1 WHERE idx=48;
INSERT INTO print_route_rule_t (shop_idx, category_idx, printer_type, also_print_at_counter)
VALUES (48, 30, 'kitchen', 1);
```

실제 웹 주문 (order_idx=37, 김치찌개) 후 print_job_t에 자동 생성:

```
job_idx=9   shop_idx=48  order_idx=37  printer_type=kitchen  status=queued
job_idx=10  shop_idx=48  order_idx=37  printer_type=counter  status=queued
```

페이로드 내용 정확:
- `table_name`: "6"
- `order_time`: "2026-05-13 10:55:24"
- `items`: [{"name":"김치찌개","qty":1,"options":[]}]
- 한글 깨짐 없음 (`JSON_UNESCAPED_UNICODE` 정상 동작)

`also_print_at_counter=1` 정책으로 kitchen + counter 동시 생성 ✅

error_log:
- `[print] webhook send failed: Could not connect to ...` (Server C 미존재 — 정상)

## 5. 디버깅 과정 메모

검증 첫 시도에서 print_job_t에 row가 생성되지 않아 다음 진단 흐름을 거침:

1. `shop_t.print_enabled=1` + 라우팅 규칙 등록 + 주문 INSERT 정상 — 모든 조건 충족 확인
2. `[print:debug]` 임시 로그 추가했으나 메시지 미출력 (사용자가 `/var/log/httpd/error_log` 확인, 실제 경로는 `/var/log/php/php_errors.log`)
3. OPcache 점검 → `validate_timestamps=On, revalidate_freq=2` 정상 → 캐시 문제 아님
4. `_print_hook_diag.php` 진단 페이지로 함수 직접 호출 → 모든 데이터 조건 일치, 그러나 print_job 생성 0건
5. 결정적 단서: 진단 페이지 출력의 `"sh_idx":48` — orders_t는 `sh_idx`이고 D3 함수는 `shop_idx`로 읽고 있었음 → 버그 수정

**향후 시사점**: 진단 페이지를 일찍 사용했으면 더 빨리 잡았을 것. 운영 디버깅 시 임시 진단 PHP 스크립트가 가장 결정적인 도구.

## 8. Phase 2로 넘어갈 때 알아야 할 것

- 현재 PHP는 `https://barorez.com/printsvc/webhook/print` (또는 `http://127.0.0.1:3000/webhook/print`)에 fire-and-forget으로 webhook을 발송함. 응답 없으므로 error_log에 `webhook send failed` 메시지가 계속 쌓이는 중 (운영 영향 없음)
- 활성 매장 sh_idx=48에서 주문이 발생할 때마다 print_job_t에 kitchen + counter row가 누적되는 중. Server C나 클라이언트가 없으므로 status=queued 영원히. Phase 2에서 정리 또는 status='failed' 일괄 업데이트 검토
- HMAC 시크릿 (`PRINT_SHARED_SECRET`)이 이미 운영 환경에 설정됨. Phase 2 Server C에서 동일 시크릿으로 webhook 수신·검증 필요. 환경 변수 또는 secrets에서 PHP의 그 값을 그대로 사용
- 시크릿 회전 권장 사항 [D004](D004.Phase1_D6_D7_D4_HMAC_ACK수신.md#7) 여전히 유효 — Phase 2 시작 전 회전 권장
- 매장 FK 컬럼명 비일관성(`sh_idx` vs `shop_idx`)은 Phase 2 Server C에서도 만날 수 있음. PHP가 보내주는 webhook 페이로드의 `shop_id`는 신규 컬럼명에 따라 정의됨
