## 1. 한 줄 요약
`asyncio` + `websockets` 기반 Server C 클라이언트. **인증 → print_job 수신 → ESC/POS 빌드 → RAW 출력 → ACK** 전 흐름을 폐쇄 루프로 구성. 중복 job_id 24h 캐시, 재접속 시 `last_known_job_id` 송신, 지수 백오프(1s → 30s → 5min) 까지 본 단위에서 닫음. 단, 실 운영 서버 연결 검증은 사용자가 admin 세션 쿠키 발급 + register 후 수행할 예정 — 본 worklog 의 §3 끝.

## 3. 검증

### 3.1 state.py 단위
- empty → load → record_processed → save → reload: last_known_job_id, is_duplicate, get_printed_at 모두 영속화 통과.
- `observe_job_id` 비단조 증가 호출 시 last_known 감소 안 함 확인.
- `_prune_locked` — 24h 이전 entry 만 제거, 최근 entry 유지 확인.

### 3.2 Mock WS server end-to-end (auth/print_job/중복/ping/재접속)
로컬 `websockets.serve` 로 다음 시나리오 자동 재현:

```
[1] client connect → auth(client_id=42, caps=['kitchen'], last_known=None)
[2] server → auth_ok(client_id=42, shop_id=999)
[3] server → print_job(job_id=1001) → client print_raw 1회 → ack(printed)
[4] server → print_job(job_id=1001) 재전송 → client print_raw 추가 호출 0 → ack(printed) 만
[5] server → ping → client pong 즉시 회신
[6] server → print_job(job_id=2000) → ack(printed)
[7] server close 1000
[8] client backoff 1초 후 자동 재접속
[9] client auth 재송신 → auth.last_known_job_id == 2000 (server 측에서 확인)
```

결과:
- print_raw 호출 2회 (job 1001 + job 2000) — 중복 1회는 출력 생략 통과.
- state.last_known_job_id == 2000.
- 재접속 시 auth.last_known_job_id == 2000 송신 확인.
- 로그에 한글 포함되어도 stdout UTF-8 reconfigure 로 인코딩 오류 0.

### 3.3 운영 서버 검증 (사용자 액션, D014 진입 전 1회)
사용자가 다음 순서로 수동 검증 예정 — D014 시작 전 게이트:

```powershell
# 1) 브라우저로 https://barorez.com/mng/login.php admin 로그인
# 2) 개발자도구 > Application > Cookies 에서 `barorez` 쿠키 값 복사
# 3) 토큰 발급 CLI 실행
python -m client_python.tools.register_client `
  --base https://barorez.com `
  --cookie "barorez=<복사한값>" `
  --shop 48 `
  --name "테스트 카운터 PC" `
  --caps kitchen `
  --write-config client_python/config.ini

# 4) [printer].name 만 추가 확인 후 데몬 기동
python -m client_python.tools.run_client

# 5) 매장에서 실제 주문 1건 발생 시 → 영수증 1장 자동 출력
```

확인 포인트:
- "auth_ok client_id=X shop_id=48" 로그 표시.
- 주문 발생 시 "job_id=YYY printed (NNN bytes)" 로그 표시 + 실제 영수증 인쇄.
- DB 직접 조회: `SELECT status, printed_at FROM print_job_t WHERE job_idx=YYY` → `status='printed'`.
- Ctrl+C 후 재기동 시 auth 메시지에 `last_known_job_id` 포함 확인 (Server C 로그).

## 4. 계획 대비 차이

| 항목 | 003 계획서 | 실제 (D013) | 사유 |
|---|---|---|---|
| 영속화 매체 | SQLite 또는 파일 (계획서 §3.2) | JSON 파일 단일 (`state/state.json`) | 사용자 결정. 의존성 0, 디버그 쉬움. Phase 5 C# 이행 시 SQLite 도 검토 가능 |
| 토큰 발급 방식 | 수동 SQL INSERT (계획서 §3.10) | Python CLI (`register_client.py`) 신규 | 사용자 결정. 재사용 가능, 매번 SQL 작성 회피 |
| 클라이언트 측 ping 송신 | 003 계획서 §3.2 "ping/pong 30초" | 클라이언트는 송신 안 함 (server.ts 가 보냄) | server_c/src/ws/server.ts 가 30초 주기로 ping 전송, 클라이언트는 pong 만 회신하면 됨. 양측 ping 중복 회피 |
| 백오프 상한 | 5min (계획서 §3.2 그대로) | 1s → 2x 증가 → 300s 상한 + auth-error 60s 즉시 슬립 + replaced 30s | auth-error (4002/4003/4004) 는 즉시 재시도해도 의미 없으므로 60초 고정, 4005(replaced) 는 30초 — close code 별 분기로 정교화 |
| 동시성 모델 | 003 계획서 미정 | print_job 처리는 `asyncio.create_task` + `asyncio.to_thread(print_raw)` | 출력 진행 중에도 ping 응답 가능. 단일 클라이언트당 출력은 어차피 직렬 (프린터 큐) — 다중 큐잉은 Print Spooler 가 처리 |
