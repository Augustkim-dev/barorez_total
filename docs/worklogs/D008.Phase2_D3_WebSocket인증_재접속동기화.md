## 4. 핵심 결정 / 비의도적 발견

### 4.1 인증 close code 매핑 (4001~4006 사용)
| code | 사유 |
|---|---|
| 4001 | auth timeout (5초 내 첫 메시지 없음) |
| 4002 | invalid auth message (잘못된 첫 메시지 형식) |
| 4003 | invalid token (PHP 검증 실패) |
| 4004 | no matching capabilities (client 주장 vs DB 교집합 없음) |
| 4005 | replaced by new connection (같은 client_id 재접속) |
| 4006 | pong timeout (30초 ping 2회 무응답) |

### 4.2 capability 교집합 정책
- client 가 `["kitchen","bar"]` 주장하지만 DB 에 `kitchen` 만 등록되어 있으면 effective = `["kitchen"]`
- 양쪽 교집합 비어있으면 4004 close (DB 가 진실)
- 운영적으로 client 가 새 프린터 추가 시 Admin UI 에서 capability 갱신 후 client 재접속 필요

### 4.3 캐시 키 hashing
- LRU 캐시 키로 평문 토큰을 그대로 쓰지 않고 `HMAC(client_id:token, PRINT_SHARED_SECRET)` 사용
- 이유: 메모리 덤프나 디버거 attach 시 토큰 노출 회피
- 5분 후 어차피 폐기되지만 보수적 결정

### 4.4 ack 메시지는 D009 로 미룸
- 본 단계 ws/server.ts 의 ack 핸들러는 로그만 남김 (`event: ack_received_stub`)
- 진짜 ACK 처리(SQLite markPrinted, PHP 콜백) 는 D009 에서 디스패처와 함께

### 4.5 PHP 호출 실패 시 negative caching 정책
- fetch 자체 실패(네트워크/타임아웃) → 캐시에 저장하지 않음 (일시적 장애 후 재시도 허용)
- HTTP 200 + `{valid: false}` → 캐시에 저장 (실제 거부, 5분 동안 반복 거부)

## 5. 검증

### 5.1 단위 검증 (모두 통과)
- `npm run typecheck` 통과 (strict TS, noUncheckedIndexedAccess)
- `npm run dev` 후 ws://127.0.0.1:3000/ws 연결:

| 케이스 | 결과 | 비고 |
|---|---|---|
| A: open 후 5초 무응답 | close 4001 "auth timeout" elapsed=5020ms | ✅ 정확 |
| B: 잘못된 첫 메시지 (`{type:'pong'}`) | recv `{auth_fail: invalid auth message}` + close 4002 | ✅ |
| C: 임의 토큰 (PHP 도달 불가, fetch error) | recv `{auth_fail: invalid token}` + close 4003 | ✅ — clientAuth.ts 가 fetch error 를 `{valid:false}` 로 정규화 |

### 5.2 미수행 검증 (D011 통합 검증으로 이월)
- PHP `api/print_clients_verify.php` 실제 200 응답 흐름 — 본 PC 에 PHP-FPM 부재
- 정상 인증 성공 후 `auth_ok` 수신 + 재접속 동기화 일괄 Push
- 같은 `client_id` 재접속 시 이전 연결 close 4005 후 신규 연결 정상 인증
- ping/pong 30초 사이클 (단위 검증 시 timeout 길어 skip)

D011 에서 다음 흐름으로 통합 검증:
1. 운영 cfg/config.inc.php `PRINT_CLIENT_TOKEN_SALT` 설정 + Server C `.env` 동기화
2. `POST /api/print_clients_register.php` (admin 세션) → plain_token 발급
3. wscat 또는 curl --include 로 wss://barorez.com/printsvc/ws 접속 + auth → auth_ok 수신
4. PHP 활성 매장에서 주문 발생 → Server C 큐 적재 → 접속 client 에 즉시 Push (D009 후) 또는 재접속 시 sync (D008 가능)

## 6. 주의사항

### 6.1 D008 코드의 PHP 호출 한계
- `php/clientAuth.ts` 는 `PHP_API_BASE + '/api/print_clients_verify.php'` 로 호출
- 운영 환경에서는 https://barorez.com 도달 가능. 개발 머신은 PHP-FPM 부재 → 매번 valid:false
- PHP 통합은 D011 (Apache 프록시 + 운영 검증) 에서

### 6.2 `print_client_t.auth_token_hash` 컬럼은 sha256 hex (길이 64)
- 스키마는 VARCHAR(128) 으로 여유 — 향후 base64 변경 시에도 무리 없음
- 본 D008 구현은 hex 만 사용

### 6.3 토큰 발급 보안
- `api/print_clients_register.php` 응답에 평문 토큰 포함 → HTTPS 위에서만 호출해야 함
- 개발 시 http://localhost:8080 으로 호출하면 토큰 노출 위험
- Phase 4 Admin UI 가 도착하면 UI 안에서 토큰을 표시하고 즉시 모달 닫기 UX 권장
