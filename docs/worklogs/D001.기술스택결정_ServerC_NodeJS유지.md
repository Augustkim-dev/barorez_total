## 1. 배경

사용자가 PRD §10.1의 Server C 런타임 선택(Node.js + TypeScript)에 대해 질문을 제기:

> "이거 서버가 apache 서버에 php로 메인 서비스를 하고 있는데, 그 서버에 node.js와 ts로 작업하는 것보다는 그냥 php로 하는 게 낫지 않아? node.js가 더 나은 이득이 있는 부분이 있는 거야?"

PRD §10.1은 Node.js 채택 이유로 "WebSocket 생태계 성숙, 비동기 I/O 최적"만 명시하고 있었고, **PHP 대안(Workerman, Swoole, Ratchet) 검토 흔적이 없었다.** 이 누락은 합리적 지적이었다.

## 2. 조사 결과

Explore 서브에이전트로 현재 코드베이스의 PHP 비동기/WebSocket 라이브러리 상태를 확인.

| 항목 | 결과 |
|---|---|
| PHP 버전 | 8.2+ (`vendor/composer/platform_check.php`) |
| Ratchet / ReactPHP / Workerman / Swoole | **모두 미설치** |
| elephant.io v4.7.3 | 존재 (Socket.IO **클라이언트** — 서버 구현 불가) |
| 백그라운드 데몬/cron worker | 흔적 없음 |
| 호스팅 | 전용 서버/VPS + root 권한 (사용자 확인) |

## 3. 사용자에게 제시한 트레이드오프

핵심 통찰: **"기존 Apache + PHP에 자연스럽게 얹는다"는 직관은 착시**. WebSocket 허브는 장시간 실행 데몬이므로 PHP든 Node.js든 별도 프로세스 + 리버스 프록시 구조가 필요. 즉 양쪽 모두 기존 mod_php 요청-응답 모델과는 다른 패러다임.

| 옵션 | 검토 결과 |
|---|---|
| PHP (Workerman) | 기술적 가능. 100매장/1,000연결 충분. 단 신규 도입·학습 비용 발생, 통합 이점 부재. |
| PHP (Swoole) | 동일. C 확장 설치 필요. |
| Node.js + TS | `ws` 업계 표준, TS 타입, 팀의 기본 경험. |

## 4. 의사결정 (AskUserQuestion 결과)

| 질문 | 답변 |
|---|---|
| Server C 기술 스택 결정 | **Node.js + TS (PRD 원안 유지)** |
| 팀의 Node.js/TS 경험 | 기본은 있음 |
| 호스팅 환경 | 전용 서버 / VPS (root 권한) |

위 조건에서 Node.js의 우위(생태계 성숙도, 타입 안전성, 학습 부담 낮음, 분리 가능 설계 자연스러움)를 채택.
