## 1. 배경

사용자가 Phase 1 계획서의 DB 마이그레이션 항목에 대해 우려를 제기:

> "phase 1에서 db의 변경이 있는데 기존 db를 너무 많이 변형하고 싶지 않은데 얼마나 변경이 되는지 예측 가능해?"

PRD §5.1은 신규 테이블 3개를 명시하나, **기존 테이블 변경 여부에 대한 사전 평가가 계획서에 정량적으로 정리되어 있지 않았다.** 또한 Phase 1 계획서 §6에 미해결로 남겨두었던 두 개의 결정사항(카테고리 참조 컬럼, FK 제약 강도)이 함께 정리될 필요가 있었다.

## 2. 조사 결과

Explore 서브에이전트로 `db/baro_sample_backup.sql` 검토.

| 확인 항목 | 결과 |
|---|---|
| 메뉴-카테고리 관계 | `shop_menu_t.sc_idx → shop_category_t.idx` |
| `orders_t` PK | `idx` |
| `orders_t.ct_snapshot` JSON 컬럼 | 존재 (페이로드 빌더에서 활용 가능) |
| `shop_t` PK | `idx` |
| 신규 FK 참조 대상 테이블 엔진 | 모두 InnoDB |

## 3. 정량 평가 결과

| 변경 종류 | 수량 | 상세 |
|---|---|---|
| 기존 테이블 컬럼 추가 | **0** | `orders_t`, `shop_t`, `shop_category_t`, `shop_menu_t` 모두 그대로 |
| 기존 테이블 인덱스 추가 | **0** | 기존 FK/조회 패턴으로 충분 |
| 기존 테이블 ALTER | **0** | 어떤 형태의 변형도 없음 |
| 신규 테이블 추가 | **3** | `print_client_t`, `print_route_rule_t`, `print_job_t` |
| 신규 인덱스 (신규 테이블에만) | **2** | `print_job_t(shop_idx, status, created_at)`, `print_client_t(shop_idx, is_active)` |

**핵심 통찰**: PRD가 hook 패턴으로 설계되어 있어 기존 테이블에 컬럼이 필요 없다. FK 컬럼은 모두 신규 테이블 쪽에만 존재.

## 4. 사용자 결정 (AskUserQuestion 결과)

| 질문 | 답변 |
|---|---|
| 신규 3개 테이블의 FK 제약 강도 | **INDEX만 추가, FOREIGN KEY 제약 없음** |
| 마이그레이션 SQL 초안 작성 시점 | **실제 구현 단계에서 작성** (계획서에는 명세 개요만) |

FK 제약 없음을 채택한 이유:
- CLAUDE.md에 명시된 "기존 데이터가 다른 시스템에서 마이그레이션되어 idx 갭/정합성 깨짐 가능"
- 본 프로젝트의 기존 컨벤션이 FK 제약을 잘 쓰지 않음
- 정합성은 PHP 코드에서 보장 (INSERT 전 존재 확인 / 끊어진 참조 시 NULL·skip 처리)

이로써 카테고리 참조 컬럼 결정도 자동으로 정리: `print_route_rule_t.category_idx`는 `shop_category_t.idx`를 **논리적으로** 참조하지만 FK 제약은 없음.
