## 0. 기술 스택 결정 근거 (Node.js + TypeScript 선정)

본 프로젝트의 메인 서비스가 PHP 8.2 + Apache로 운영되고 있어 "Server C도 PHP로 통합하는 것이 자연스럽지 않은가"라는 질문이 제기되었다. 검토 결과 다음과 같이 결정한다.

### 비교

| 옵션 | 결론 | 사유 |
|---|---|---|
| PHP (Workerman) | ❌ | 기술적으로 가능. 100매장/1,000연결도 충분. 단, 현재 `vendor/`에 해당 라이브러리가 없어 신규 도입·학습 비용 발생. 결정적으로 "기존 Apache+PHP에 자연스럽게 얹는다"는 통합 이점이 **없다** — 어차피 별도 데몬 + 리버스 프록시 구조. |
| PHP (Swoole) | ❌ | 동일. Swoole은 C 확장 설치 필요. VPS에서는 가능하나 기존 PHP-FPM과의 공존 운영 비용. |
| **Node.js + TS** | ✅ **채택** | (1) `ws` 라이브러리가 WebSocket 허브의 사실상 업계 표준, (2) TS 타입으로 PRD §7 메시지 프로토콜의 강타입 공유 가능, (3) 팀이 기본 Node.js 경험 보유 → 학습 부담 낮음, (4) PRD §3.3 "분리 가능 설계" 원칙을 자연스럽게 만족 (별도 프로세스/별도 런타임). |

### 환경 조사 사실 (2026-05-12 기준)

- PHP 8.2+ 사용 중 (현대적 버전)
- Ratchet / Swoole / Workerman / ReactPHP **모두 미설치**
- elephant.io v4.7.3만 존재 (Socket.IO **클라이언트** — 서버 구현 불가)
- 백그라운드 데몬/cron worker 흔적 없음
- 호스팅: 전용 서버/VPS + root 권한 (양쪽 스택 모두 제약 없음)

### 재검토 트리거

- 팀 인력 구성이 PHP 전담으로 바뀌고 Node.js 유지보수가 어려워지는 경우
- 운영상 단일 스택 강제 요구가 생기는 경우

---

## 1. 목적

PHP와 매장 PC를 중계하는 **WebSocket 허브**를 구축한다. 본 Phase가 완료되면 다음이 가능해야 한다.

- PHP의 Webhook을 받아 작업 큐에 적재한다.
- 매장 client(WS)가 인증/접속한 상태를 유지하고, 적절한 client에 Push한다.
- ACK를 수신하여 PHP에 결과를 통보한다.
- 재시도/재접속 동기화/오프라인 큐를 모두 처리한다.

## 3. 세부 작업 항목

### 3.1 프로젝트 초기화

- [ ] `server_c/` 디렉토리 생성, `package.json` (Node.js 20 LTS)
- [ ] TypeScript 설정 (`tsconfig.json`, strict mode)
- [ ] 의존성: `ws`, `express`, `better-sqlite3`, `pino`, `pino-pretty`(dev), `dotenv`, `zod`(payload 검증), `node-fetch`(또는 fetch 내장)
- [ ] dev 의존성: `typescript`, `ts-node-dev`, `@types/*`, `vitest`
- [ ] 빌드 스크립트 (`tsc` → `dist/`), 실행 스크립트, 테스트 스크립트
- [ ] `.env.example` 작성: `PORT`, `PRINT_SHARED_SECRET`, `PHP_API_BASE`, `SQLITE_PATH`, `LOG_LEVEL`

### 3.2 Webhook 수신 (PHP → Server C)

PRD §7.1.

- [ ] Express 앱 셋업, raw body 보관 (HMAC 검증에 필요)
- [ ] `POST /webhook/print` 핸들러
- [ ] HMAC-SHA256 검증 (timing-safe equal), 실패 시 401
- [ ] zod 스키마로 본문 검증: `{ job_ids: number[], shop_id: number }`
- [ ] 작업을 내부 큐(SQLite)에 INSERT (status=queued)
- [ ] 즉시 200 응답 (Push는 비동기)

### 3.3 WebSocket 서버 + 인증

PRD §6, §7.4.

- [ ] `ws` 기반 서버, HTTP 서버와 같은 포트 공유 (upgrade 처리)
- [ ] WSS는 Apache 리버스 프록시에서 TLS 종료 → Server C 내부는 평문
- [ ] 연결 직후 첫 메시지 5초 내 미수신 시 강제 종료
- [ ] `type=auth` 메시지 검증: `client_id`, `token`, `capabilities`, `app_version`, `last_known_job_id`
- [ ] PHP API로 토큰 검증 — 매번 호출하지 말고 메모리 캐시(LRU, 5분 TTL) 사용
  - 또는 Server C 부팅 시 `print_client_t` 전체를 PHP API로 한 번에 받아 캐시 → 토큰 갱신 시 invalidate webhook
- [ ] 인증 성공 시 `{ "type": "auth_ok" }` 회신
- [ ] 인증 성공 후 `last_known_job_id` 이후의 미전송 작업 일괄 Push (PRD §8.3)
- [ ] ping/pong 30초 주기, 연속 2회 무응답 시 종료 (PRD §7.6)

### 3.4 client 매칭 + Push 디스패처

PRD §6.2.

- [ ] 메모리 자료구조: `Map<shop_id, Map<client_id, ClientConnection>>`
- [ ] 작업 디스패치: `shop_id + printer_type(capability)` 으로 후보 client 검색
- [ ] 같은 capability 보유 client 다수 시 우선순위 (open question — 일단 `client_idx` 작은 쪽 또는 last_connected 최근)
- [ ] Push 메시지 직렬화 (PRD §7.2), 전송 + `status=sent`, `sent_at` 업데이트

### 3.5 SQLite 영속화

PRD §10.1.

- [ ] 스키마: `jobs(job_id, shop_id, printer_type, payload_json, status, attempt_count, assigned_client_id, last_error, sent_at, printed_at, created_at, next_retry_at)`
- [ ] `clients_cache(client_id, shop_id, capabilities, auth_token_hash, last_seen)` (선택)
- [ ] 부팅 시 `status IN ('queued','sent')` 작업 복구

### 3.6 ACK 처리 + 재시도

PRD §8.1, §8.2.

- [ ] WS 메시지 `type=ack` 수신 → SQLite 업데이트 → PHP 콜백
- [ ] ACK 미수신 타임아웃 10초 → 재시도 큐에 등록
- [ ] 백오프 1s → 3s → 10s, 최대 3회 → 3회 모두 실패 시 `status=failed`
- [ ] 매장 client 미접속 상태에서 webhook 도착 → `status=queued` 유지 (Push만 보류)

### 3.7 PHP 콜백

- [ ] `PATCH {PHP_API_BASE}/api/print-jobs/{id}/status` (PRD §7.5)
- [ ] HMAC 서명 부착, 5초 타임아웃
- [ ] 실패 시 자체 재시도 (1s → 5s → 30s)

### 3.8 중복 방지

PRD §8.4 — client 측에서 캐시하지만 Server C에서도 동일 job_id 재전송이 짧은 간격으로 발생하지 않도록 in-flight set 관리.

### 3.9 헬스체크 + 로깅

- [ ] `GET /health` → `{ uptime, connections, queue_size, error_count }`

### 3.10 PM2 + Apache 리버스 프록시

- [ ] `ecosystem.config.js` — fork 모드, max_memory_restart, log rotation

## 4. 작업 순서

1. 프로젝트 초기화 + 빈 Express 앱 (D1)
2. SQLite 영속화 + 스키마 (D5)
3. Webhook 수신 + HMAC 검증 + 큐 적재 (D2) → cURL로 검증
4. WebSocket 서버 + 인증 (D3) → `wscat`으로 검증
5. Push 디스패처 (D4) → 인증된 WS 클라이언트로 echo 시험
6. ACK 처리 + 재시도 (D6)
7. PHP 콜백 (D7) → Phase 1 결과물과 연결
8. 미접속/재접속 동기화
9. 헬스체크 + 로깅 (D8)
10. PM2 + Apache 프록시 (D9, D10)
