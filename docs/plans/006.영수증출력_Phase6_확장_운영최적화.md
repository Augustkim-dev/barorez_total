# 006. Phase 6 — 확장 및 운영 최적화

| 항목 | 내용 |
|---|---|
| Phase | 6 / 6 |
| 일정 | 8주차 이후 (연속 운영) |
| 영역 | 다중 매장 운영, Redis 이전 검토, Server C 분리, 모니터링/알림 강화 |
| 선행 의존성 | Phase 1~5 모두 완료, 본 빌드 클라이언트가 다수 매장에 배포된 상태 |

---

## 1. 목적

PRD §2.3 성공 지표 중 **확장 단계 (10개 매장)** 와 **운영 단계 (100개 매장)** 기준을 만족시키고, 향후 Server C를 PHP/DB와 물리적으로 분리할 수 있도록 운영 환경을 정비한다.

> ⚠️ 본 Phase는 **시한 작업이 아니라 운영 활동**이다. 트래픽이 임계치에 가까워질 때 트리거되는 항목과, 시점에 무관하게 즉시 시작 가능한 항목을 구분한다.

## 2. 산출물 (Deliverables)

| # | 산출물 | 트리거 |
|---|---|---|
| D1 | 다중 매장 운영 모니터링 대시보드 | 매장 수 ≥ 5 |
| D2 | UptimeRobot / Cronitor 외부 헬스체크 설정 | 본 빌드 출시 즉시 |
| D3 | Server C 자동 재시작 + SMS 알림 | 본 빌드 출시 즉시 |
| D4 | SQLite → Redis 이전 (ioredis) | SQLite WAL 잠금 경합 발생 시 또는 동시 client > 200 |
| D5 | Server C 독립 인스턴스 분리 | PHP 서버 CPU/RAM 경합 발생 시 |
| D6 | 다중 인스턴스 + 부하 분산 (선택) | 동시 client > 1,000 |
| D7 | 매장 사장님 모바일 출력 상태 화면 (PRD §14.3) | 점주 요청 누적 시 |
| D8 | EV 코드 서명 도입 (PRD §10.3) | 매장 수 ≥ 20 또는 SmartScreen 클레임 누적 시 |
| D9 | 운영 런북 (장애 대응 매뉴얼) | 본 빌드 출시 직후 |
| D10 | 매장별 SLA 리포트 (월간) | 운영 안정 후 |

## 3. 세부 작업 항목

### 3.1 모니터링 / 알림 강화

PRD §12.1, §12.2.

- [ ] Server C `/health` 엔드포인트에 메트릭 노출 (uptime, active_connections, queue_size_by_shop, push_p95_ms, error_rate_5min)
- [ ] 외부 모니터링 (UptimeRobot or Cronitor) 1분 단위 헬스체크 등록
- [ ] 알림 채널 정의: Server C 다운 → 운영자 SMS / Slack
- [ ] 매장 PC 1시간 이상 미접속 → 점주에게 알림 (영업 시간 내에만 발송)
- [ ] 출력 24시간 미전송 작업 → 관리자 SMS/이메일 (PRD §8.3)
- [ ] Admin UI 대시보드에 매장별 출력 실패율, 평균 지연 그래프 추가

### 3.2 SQLite → Redis 이전 검토

PRD §10.1, §13 Phase 6.

- [ ] 임계치 정의: 동시 client > 200 또는 큐 처리 p95 > 500ms 또는 SQLite WAL 경합 로그
- [ ] 임계치 도달 시 Redis 마이그레이션 작업 계획:
  - `ioredis` 도입, 큐 자료구조 설계 (Lists + Hashes 또는 Streams)
  - 양립 가능한 추상 인터페이스를 Phase 2에서 미리 두었는지 점검 (필요 시 리팩토링)
  - 마이그레이션 윈도우: 점진적 dual-write → cutover
- [ ] Redis 운영: AOF + RDB 백업, 메모리 한도, eviction policy

### 3.3 Server C 분리

PRD §3.3.

- [ ] PHP/DB 서버와 Server C를 별도 인스턴스로 이전
- [ ] 통신은 HTTP만 사용 (현재 설계가 이미 충족 — 점검만)
- [ ] 환경 변수 (`PRINT_SERVER_URL`, `PHP_API_BASE`) 갱신
- [ ] HMAC 시크릿이 두 서버에 동일하게 배포되도록 시크릿 관리 (Vault, 환경 파일 동기화)
- [ ] DNS / 방화벽 / TLS 인증서 작업

### 3.4 다중 인스턴스 (필요 시)

PRD §14.1 (Server C 단일 장애점).

- [ ] WebSocket sticky-session 또는 Redis pub/sub로 인스턴스 간 client 라우팅 공유
- [ ] HA 구성: 최소 2 인스턴스, 앞단에 LB(HAProxy/Nginx)
- [ ] 헬스체크 기반 자동 fail-over

### 3.5 매장 사장님 화면 (PRD §14.3)

- [ ] 본 Phase 시작 시 점주 피드백 수렴 → 모바일 앱 vs `market/` 메뉴 결정
- [ ] 결정에 따라 별도 mini-plan으로 분리하여 작업

### 3.6 EV 코드 서명

PRD §10.3, §14.1.

- [ ] EV 인증서 발급 (DigiCert/Sectigo)
- [ ] 빌드 파이프라인에 서명 단계 추가 (`signtool.exe` 또는 Velopack의 서명 옵션)
- [ ] 첫 서명 출시 후 SmartScreen 평판 누적 모니터링

### 3.7 운영 런북

- [ ] Server C 다운 시 복구 절차
- [ ] DB 마이그레이션 충돌 대응
- [ ] 토큰 유출 의심 시 일괄 재발급 스크립트
- [ ] 매장 PC 원격 재설치 절차
- [ ] 장애 후 미전송 작업 일괄 처리 SQL

### 3.8 PRD open questions 수렴

PRD §14.3.

- [ ] 같은 capability 다중 client 우선순위 정책 → 운영 데이터로 결정 후 PRD 갱신
- [ ] 지원 프린터 모델 목록 공식화 (호환성 테스트 매트릭스)
- [ ] 영업종료 시 client 종료 정책 (항상 켜둠 결론 — 운영 데이터로 검증)
- [ ] 매장 사장님 화면 분리/통합 결정

## 4. 작업 순서

본 Phase는 **트리거 기반**이다. 다음 순서로 우선순위를 매긴다.

1. 즉시 (Phase 5 출시 직후): D2(외부 헬스체크), D3(자동 재시작/알림), D9(운영 런북)
2. 매장 5개 도달: D1(다중 매장 대시보드 강화)
3. 매장 10개 / 첫 SmartScreen 클레임: D8(EV 코드 서명)
4. 임계치 도달: D4(Redis 이전), D5(Server C 분리)
5. 점주 요청 누적: D7(매장 사장님 화면)
6. 대규모 확장: D6(다중 인스턴스)

## 5. 완료 기준

본 Phase는 종결이 아니라 **운영 상태 유지**가 목표이다. 다음을 만족하면 Phase 6의 1차 목표 달성으로 본다.

- [ ] PRD §2.3 확장 단계 (10개 매장 동시 운영, 평균 지연 < 1초) 충족
- [ ] PRD §14의 모든 위험 항목에 대해 운영 데이터 기반 대응이 정의됨
- [ ] PRD §14.3 open questions 4건 모두 결론 또는 별도 Phase로 이관
- [ ] 운영 런북 작성 + 운영팀 인수인계
- [ ] 분기 단위 SLA 리포트 자동화
