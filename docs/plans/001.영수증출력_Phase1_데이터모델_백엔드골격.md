## 0. DB 변경 영향도 (사전 평가)

본 Phase는 **기존 테이블을 전혀 건드리지 않는다.** 모든 변경은 신규 테이블 3개와 그 위의 인덱스에 한정된다.

| 변경 종류 | 수량 | 상세 |
|---|---|---|
| 기존 테이블 컬럼 추가 | **0** | `orders_t`, `shop_t`, `shop_category_t`, `shop_menu_t` 모두 그대로 |
| 기존 테이블 인덱스 추가 | **0** | 기존 FK/조회 패턴으로 충분 |
| 기존 테이블 ALTER | **0** | 어떤 형태의 변형도 없음 |
| 신규 테이블 추가 | **3** | `print_client_t`, `print_route_rule_t`, `print_job_t` |
| 신규 인덱스 (신규 테이블에만) | **2** | `print_job_t(shop_idx, status, created_at)`, `print_client_t(shop_idx, is_active)` |

**왜 0건 변경인가**: PRD가 hook 패턴으로 설계되었기 때문이다. 주문 INSERT 직후 PHP 코드가 신규 `print_job_t`에 row를 추가하는 방식이므로 `orders_t`에 "출력 여부" 플래그 같은 컬럼이 필요 없다. FK 컬럼(`shop_idx`, `order_idx`, `category_idx`)은 모두 **신규 테이블 쪽**에 들어가며, 기존 테이블이 참조될 뿐 변경되지 않는다.

**조사로 확정된 사실** (2026-05-12, `db/baro_sample_backup.sql` 검토):
- 메뉴-카테고리 관계: `shop_menu_t.sc_idx → shop_category_t.idx`
- `orders_t.idx` (PK), `shop_t.idx` (PK), `shop_category_t.idx` (PK) — 모두 신규 테이블 FK 컬럼의 참조 대상
- 신규 FK 참조 대상 테이블 엔진 모두 InnoDB

### 외래키(FK) 제약 정책

**FK 제약은 걸지 않는다.** 컬럼은 `shop_idx INT NOT NULL` 같은 단순 INT로 정의하고, INDEX만 추가한다.

이유:
- 기존 데이터의 참조 정합성이 깨져 있을 가능성 (CLAUDE.md의 "AUTO_INCREMENT gaps, schema was copied/migrated from another system")
- 본 프로젝트의 기존 컨벤션이 FK 제약을 잘 쓰지 않음 (정합성은 PHP에서 보장)
- 운영 중 마이그레이션·정리 작업에서 강한 제약이 오히려 장애 원인이 됨

대신 PHP 측에서 INSERT 전 존재 확인을 하거나, 끊어진 참조가 발생하면 NULL 처리하는 정책을 코드에서 명시한다.

## 1. 목적

영수증 자동 출력 시스템의 **데이터 기반**과 **PHP 측 진입/출입점**을 만든다. 본 Phase가 완료되면 Server C 없이도 다음이 가능해야 한다.

- 신규 테이블 3종(`print_client_t`, `print_route_rule_t`, `print_job_t`)이 운영 DB에 존재한다.
- 주문 발생 시 PHP가 라우팅 규칙을 보고 `print_job_t` row를 생성한다.
- Server C가 호출할 ACK 수신 API가 동작한다 (Postman/cURL로 검증 가능).
- HMAC 서명 검증 미들웨어가 모든 신규 엔드포인트에 적용되어 있다.

## 3. 세부 작업 항목

### 3.1 DB 마이그레이션 SQL 작성

PRD §5.1 스키마를 그대로 옮기되, 기존 컨벤션(`del_date`, `wdate`/`udate`)을 따른다.

**제약 정책 (§0 참조)**: FK 제약(`FOREIGN KEY ... REFERENCES`)은 걸지 않는다. 참조 컬럼은 단순 INT로 정의하고 INDEX만 추가한다.

- [ ] `print_client_t` CREATE — PK, `shop_idx INT NOT NULL` (FK 제약 없음), 토큰 해시 컬럼, 인덱스
- [ ] `print_route_rule_t` CREATE — PK, `shop_idx INT NOT NULL`, `category_idx INT NOT NULL` (논리적으로 `shop_category_t.idx` 참조, FK 제약 없음), `printer_type` ENUM
- [ ] `print_job_t` CREATE — BIGINT PK, `shop_idx INT NOT NULL`, `order_idx INT NOT NULL` (논리적으로 `orders_t.idx` 참조, FK 제약 없음), JSON `payload`, 상태 ENUM, 시도 횟수
- [ ] 인덱스 추가: `print_job_t(shop_idx, status, created_at)`, `print_client_t(shop_idx, is_active)`
- [ ] 엔진 InnoDB로 통일 (`ENGINE=InnoDB DEFAULT CHARSET=utf8mb4`)
- [ ] 롤백 스크립트 작성 (`DROP TABLE` 3종)
- [ ] 운영 적용 전 스테이징 DB에서 dry-run, `db/baro_sample_backup.sql`을 기준으로 충돌 여부 확인
- [ ] 정합성 보장은 PHP 코드에서 처리: INSERT 전 존재 확인, 또는 끊어진 참조 발견 시 NULL/skip 처리 정책 명시

### 3.2 라우팅 규칙 + print_job 생성 로직

### 3.5 ACK 수신 API

엔드포인트: `PATCH /api/print-jobs/{id}/status` (PRD §7.5). PHP는 URL 라우팅 프레임워크가 없으므로 `api/print_jobs_status.php?id=...` 형태로 구현하고 Apache rewrite가 가능하면 추가.

- [ ] HTTP 메서드 검증 (PATCH만 허용)
- [ ] HMAC 헤더 검증
- [ ] 요청 본문 JSON 파싱: `status`, `printed_at`, `client_idx`, `last_error`
- [ ] `print_job_t` UPDATE: status, sent_at/printed_at, attempt_count, assigned_client_idx, last_error
- [ ] 응답: 200 OK + 짧은 JSON `{"ok":true}`

### 3.6 수동 재출력 API

- [ ] `send_print_webhook()` 호출

## 4. 작업 순서

1. 스키마 확정 → 마이그레이션 SQL 작성 → 스테이징 적용
2. HMAC 미들웨어(D6) → 단위 테스트 (cURL)
3. ACK 수신 API(D4) → cURL로 verification (실제 Server C 없이도 동작 확인)
4. Webhook 발송 헬퍼(D3) — 이때는 PHP 자체 echo 서버로 발송 테스트
5. 페이로드 빌더 + print_job 생성 로직(D2)
6. 주문 INSERT 코드에 hook 삽입 → 실제 주문 한 건으로 end-to-end (Webhook은 404 받아도 OK)
7. 수동 재출력 API(D5)
8. 환경 변수/설정 정리(D7) + 테이블 등록(D8)
