# 004. Phase 4 — Admin UI + 라우팅 규칙

| 항목 | 내용 |
|---|---|
| Phase | 4 / 6 |
| 일정 | 4주차 |
| 영역 | PHP Admin UI 확장 (`mng/`, 일부 `market/`) |
| 선행 의존성 | Phase 1 (DB 스키마, ACK API), Phase 2 (Server C 동작 중) |
| 후행 의존성 | Phase 5 (실제 C# client 다수 등록을 위해 본 화면 필요) |

---

## 1. 목적

베타 단계까지는 수동 SQL로 처리해 온 **client 등록·라우팅·재출력**을 운영자가 GUI로 관리할 수 있게 한다. 본 Phase가 완료되면 운영팀이 SQL 없이 모든 작업을 처리할 수 있다.

## 3. 세부 작업 항목

### 3.1 매장 PC 목록 + 등록/관리 (D1, D2)

PRD §5.1.1, §6.3.

- [ ] 목록 컬럼: 매장명, PC 이름, capabilities, 마지막 접속/끊김 시각, 활성 여부, 액션 (수정/토큰 재발급/비활성화)
- [ ] 필터: 매장, 활성 여부
- [ ] 등록 폼: 매장 선택, PC 이름, capabilities 체크박스(`kitchen`/`counter`/`bar`), 활성 여부
- [ ] 저장 시 64자 랜덤 토큰 생성 → DB에는 SHA-256 + salt 해시 저장, 평문은 **1회만** 발급 직후 화면에 노출 (PRD §6.3)
- [ ] 토큰 재발급: 기존 해시 즉시 무효, 새 평문 1회 노출, Server C 캐시 invalidate(있다면)
- [ ] 비활성화: `is_active=0`, Server C에 즉시 종료 신호(선택)

### 3.2 라우팅 규칙 설정 (D3)

PRD §5.1.2.

- [ ] 매장 선택 → 해당 매장의 `shop_category_t` 목록 표시
- [ ] 카테고리별로 `printer_type` 선택 (kitchen/counter/bar)
- [ ] `also_print_at_counter` 체크박스 (기본 ON — 카운터 영수증 동시 출력)
- [ ] 일괄 저장 (BULK UPSERT)
- [ ] 미지정 카테고리는 기본 카운터로 폴백(설계 결정 필요)

### 3.3 출력 작업 로그 (D4)

PRD §4.4.

- [ ] 컬럼: job_idx, 매장, 주문번호, printer_type, status, attempt_count, assigned_client, sent_at, printed_at, last_error
- [ ] 필터: 매장, status, 기간, 주문번호
- [ ] 페이지네이션 (기본 50건)
- [ ] 상세 모달: payload JSON 표시
- [ ] 액션 버튼: "다시 출력" → `POST /api/print-jobs/{id}/retry` (Phase 1의 D5 재사용)

### 3.4 매장별 대시보드 (D5)

PRD §12.1.

- [ ] 오늘 출력 건수, 실패 건수, 평균 지연 (created_at → printed_at)
- [ ] 최근 1시간 미접속 매장 PC 목록 (운영자가 점주에게 연락하는 신호)
- [ ] 실시간성은 1분 캐시로 충분 (SSE 도입은 과한 설계)

### 3.5 매장 사장님 화면 (D7, 선택)

PRD §14.3 open question — 별도 모바일 앱 vs `market/` 메뉴.

- [ ] 1차는 `market/print/index.php`에 단순 출력 로그 + 재출력 버튼만
- [ ] 모바일 앱 통합은 별도 의사결정

### 3.6 사이드바 등록

- [ ] [mng/inc/header.sidebar.inc.php](../../web/public_html/mng/inc/header.sidebar.inc.php) (또는 동등 위치)에 새 메뉴 그룹 "영수증 출력" 추가
  - 매장 PC 관리
  - 라우팅 규칙
  - 출력 작업 로그
  - 출력 대시보드

## 4. 작업 순서

1. 사이드바 메뉴 등록 (D8) — 빈 페이지라도 먼저 라우팅 확보
2. 매장 PC 목록 + 등록 (D1, D2) — 베타 매장 client를 GUI로 재등록할 수 있어야 다음 단계 진행
3. 라우팅 규칙 (D3)
4. 출력 작업 로그 + 재출력 (D4, D6)
5. 대시보드 (D5)
6. 매장 사장님 화면 (D7, 시간 남으면)

## 5. 완료 기준

- [ ] Admin UI에서 새 client 등록 → 토큰 평문 1회 표시 → Python 클라이언트에 입력 → 정상 접속
- [ ] 토큰 재발급 시 기존 client는 인증 실패, 새 토큰으로는 성공
- [ ] 라우팅 규칙 변경 후 신규 주문이 변경된 규칙대로 출력
- [ ] 출력 로그에서 실패 건 확인 후 "다시 출력" 클릭 → 정상 재출력
- [ ] 대시보드에 오늘 통계 정상 표시
- [ ] git commit & push 완료

## 6. 위험 및 결정 필요 사항

| 항목 | 결정 필요 시점 |
|---|---|
| `shop_category_t`의 실제 컬럼 구조와 매장-카테고리 관계 — 본 프로젝트의 메뉴 카테고리 모델을 코드 확인 후 폼 설계 | 라우팅 규칙 화면 작업 시 |
| 토큰 재발급 시 Server C의 인증 캐시 무효화 방법 (Server C에 invalidate API 추가 vs TTL에 의존) | Phase 2와 협의 |
| 미지정 카테고리의 기본 출력 정책 (카운터로 폴백 vs 출력 안 함) | 라우팅 규칙 작업 시 |
| 매장 사장님 화면 (PRD §14.3 open question) — 본 Phase에 포함 vs 별도 Phase | Phase 시작 시 |
| `mt_level <= 2` 가드에 슈퍼관리자만 통과시키도록 본 화면들에 추가 가드 필요한지 | UI 작성 시 |
